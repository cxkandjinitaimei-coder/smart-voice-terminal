# 决策协议 v2 · 信封 + moves / 类型化帧

> 适用：**云端 Flask（决策生成）→ ESP8266（解析/转发）→ F407（执行）** 三方约定。
> v1 是"单条决策 `{action,value}`"；v2 升级为"**一次决策 = 一个信封，里面装任意条、任意类型、任意字段的动作队列**"，解决"一次 AI 决策要同时让舵机、表情、屏幕都动起来"的需求。
>
> **2026-09-15 补充**：新增 **§3.1.1 `@SENSOR:` 结构化上报格式**（温湿度/距离/人员在离）和
> **§3.2.1 `POST /api/data` 的 `alert` 字段** —— 这两条是云端"数据可视化 + 异常统计"的数据来源。
> 格式已定稿并被**实跑验证过**（用「测试」页造假数据），但 **F407 端还没实现**，硬件到位后照发即可。

---

## 0. 一句话流程

```
AI 决策 JSON（信封+moves）
   └─► ESP8266 用 ArduinoJson 解析，逐条 moves[] 拆成「类型化帧」
         @MOVE:servo,1,90\n
         @MOVE:gesture,nod\n
         @TEXT:你好呀\n
   └─► F407 按行解析（startsWith + split），驱动舵机 / 表情 / 屏幕文字
```

**关键点**：F407 的 Keil 工程没有 JSON 库，所以**由 ESP 负责拆帧**，F407 只用字符串就能解析。云端返回多少条、每条字段是什么，**每次都不固定**，三方都不做硬编码。

## 1. 决策信封 JSON（云端 → ESP）

```json
{
  "message": "你好呀，我看到你啦",
  "text": "你好呀",
  "moves": [
    {"type": "servo",      "id": 1, "angle": 90},
    {"type": "servo",      "id": 2, "angle": 10},
    {"type": "gesture",    "name": "nod"},
    {"type": "expression", "face": "happy"}
  ],
  "raw": "AI 原始输出（日志用）"
}
```

### 1.1 信封字段

| 字段 | 必填 | 含义 |
|---|---|---|
| `message` | ✅ | 机器人要"说"/显示的话（屏幕文字、语音等），受字库白名单约束，简短口语化 |
| `text` | ❌ | 独立的短显示文字；不想把整句 message 都怼上屏时单独用 |
| `moves[]` | ✅ | 物理动作队列。**条数不固定、每条字段不固定**，按先后顺序执行；无动作时是 `[]` |
| `raw` | ❌ | AI 原始回复全文，仅日志/调试用，F407 不需要 |

### 1.2 move 类型表（本轮支持，可扩展）

| type | 字段 | 示例 | F407 动作 |
|---|---|---|---|
| `servo` | `id`(1/2)、`angle`(0~180) | `{"type":"servo","id":1,"angle":90}` | 脖子某关节转到指定角度 |
| `gesture` | `name` | `{"type":"gesture","name":"nod"}` | F407 内置联动动作（点头/招手/左右看/摇头） |
| `expression` | `face` | `{"type":"expression","face":"happy"}` | 屏幕换表情 |

gesture.name 取值（可后续在 F407 固件里加，协议不用改）：

| name | 含义 |
|---|---|
| `nod` | 点头 |
| `hi` | 打招呼 |
| `look_left` / `look_right` | 看左 / 看右 |
| `shake` | 摇头 |

expression.face 取值：`happy` / `sad` / `sleepy` / `angry` / `normal`。

> **扩展新硬件**：以后加设备，就在 `moves[]` 里用新 `type`（如 `{"type":"motor","speed":50}`），
> ESP 未知类型会**把剩余标量字段原样逗号拼接**成 `@MOVE:motor,50` 照常转发；
> F407 认识就执行、不认识就忽略。云端 `config.json` 的 `move_types` / `rules` 同步补说明即可。
> `actions`（fan_on/ac_on/light_on/…）保留为基础动作表参考，仍可输出，按旧方式包进 moves。

## 2. 类型化帧（ESP → F407）

ESP 收到信封后，逐条 moves 拆成**一行一帧**（行分隔符 **`\r\n`**，每条参数以逗号分隔）：

> ★ **2026-09-21 订正：行尾统一是 `\r\n`（原来是 `\n`）。**
> 理由：**`\r\n` 是严格超集** —— 按 `\n` 切再 `trim()` 两者都对，按 `\r\n` **精确切**时 `\n` 结尾会把**两帧粘成一条、还不报错**。
> ★★ **真正分帧的是结尾的 `#`**（ESP 侧按它切帧；上面示例为了可读没写 `#`），**行尾只服务 `readStringUntil('\n')` 那类读取** —— **别拿行尾当帧界**。

```
@MOVE:servo,1,90\n        # 舵机1 → 90°
@MOVE:servo,2,10\n        # 舵机2 → 10°
@MOVE:gesture,nod\n       # 点头
@MOVE:expression,happy\n  # 屏幕表情 happy
@TEXT:你好呀\n            # 屏幕显示文字（text 优先，无则用 message）
```

### 2.1 文法

| 帧 | 文法 | 说明 |
|---|---|---|
| `@MOVE:servo,<id>,<angle>` | 3 段 | 脖子关节转到角度 |
| `@MOVE:gesture,<name>` | 2 段 | 内置联动动作 |
| `@MOVE:expression,<face>` | 2 段 | 屏幕表情 |
| `@MOVE:<type>,<其余标量字段原样>…` | 未知类型 | 扩展兼容：照常转发，F407 可忽略不认识者 |
| `@TEXT:<文字>` | 1 段 | 屏幕显示文字（可含逗号，不要 split 它！按 `@TEXT:` 前缀截取后面全部） |
| `@MIC:start` | 0 段 | ★ **2026-09-20 起**：开始录音，**默认 2 秒** |
| `@MIC:stop` | 0 段 | 撤回**"还没开录"**的那一次（录起来了就撤不回） |
| `@MIC:rec,<n>` | 2 段 | ★ 录 `n` 秒。**`n` = 1~99 有效**，`0` / `>99` **收下但忽略**（★ 计 `ailink_ok_cnt` **不是 drop** ⇒ 现象是"ok 涨、机器人不动"，**比 drop 难查**）。★★ **`n ≤ 2` 走老 RAM 版（录完自动 `/dump`）；`n > 2` 走流式上行（见 2.3）**；★★ **`n > 10` 被静默夹到 10**（`MICLINK_SEC_MAX_PLANNED`）⇒ **UI 必须自己封顶 10**，别指望板子报错 |

> ⚠️ **`@MIC:` 三条的匹配口径（固件侧是权威）**：**严格小写、整行 `strcmp`**（`App/ailink.c::do_mic()`），
> **`rec,` 后面只认数字、不允许空格**。网页侧正则用 `^@MIC:(start|stop|rec,[1-9]\d?)#$`（`static/page-test.js:147`）。
> ★ **"三条"是固件白名单的说法**；`@MIC:rec,<n>` 这一条**按 `n` 分两条路径**（RAM / 流式），别当成两种帧。

### 2.2 F407 侧解析建议（下一轮实现，字库到位后）

按行收帧，不需要 JSON 库：

```
收到一行 line：
  line.startsWith("@MOVE:") → 去掉前缀 @MOVE:，再按 ',' 切出 type 与参数
      切出来第 1 段是 type：
        "servo"       → 第2段=id，第3段=angle，调 ServoX_SetAngle(angle)
        "gesture"     → 第2段=name，查表执行联动动作
        "expression"  → 第2段=face，刷新屏幕表情
        其它         → 忽略（或打印调试）
  line.startsWith("@TEXT:") → 去掉前缀 @TEXT:，**整段**交给屏幕字库渲染
  line.startsWith("@SENSOR:" / "@USER:" / "@ALERT:") → 这是 F407 自己发的上行帧，不会收到
```

### 2.3 ★★ 二进制帧信封（F407 ↔ ESP 的 UART 上，与上面的文本行**共存**）★ 2026-09-21 新增

> ★ **这一段只在 F407 ↔ ESP 之间**（PC / 云端的登记见 3.4）。权威定义在 `合作表.md §4.3`，这里只是把它补进本协议。

```
0xA5 0x5A | type(1) | seq(2, LE) | len(2, LE) | payload[len] | xor(1)
```

- **`xor`** = 从 `type` 到 `payload` 末尾的**滚动异或**（**含** `seq`/`len` 那 4 字节，**不含**两个同步字节）
- **线上总长 = 8 + len**
- **type 段**：`0x01~0x0F` = **01语音** / `0x10~0x1F` = **02OTA** / `0x20` 以上保留

**为什么必须开这条旁路**：`ESP_UART_GetLine()` 把 `0x00` 当致命（`ch == 0` ⇒ 整行作废）、行长上限 192 字节，
而 PCM 里 `0x00` 是**必然出现**的 ⇒ **二进制载荷绝不能走那条行路径**。所以 `ESP_UART_GetMsg()` **能同时收两种**，
**文本仍走原来的行逻辑**（`ESP_UART_GetLine()` 的语义与返回码**逐字未动** —— PC 上的回归口靠这个）。

**01 语音的四个 type（ESP 侧状态机必须认识）**

| type | 名 | 方向 | payload |
|---|---|---|---|
| `0x01` | 音频开始 | F407→ESP | `seconds(2) total(4) rate(2) bits(1) ch(1)` = **10 B** |
| `0x02` | PCM 块 | F407→ESP | 裸 PCM（**`seq` = 块号**，一块 = 2048 B = 1024 样本 = 64 ms） |
| `0x03` | 音频结束 | F407→ESP | `sent(2) chunks_ok(2) lost_half(2)` = **6 B**（对账用） |
| `0x04` | **流控回执** | ESP→F407 | `flags(1)`：`0` = 继续发 `next_seq`、`1` = **从 `next_seq` 重传**。★ **`next_seq` 就用信封自己的 `seq` 字段**，不在 payload 里再塞一遍 |

★ **`0x04` 的来源变了、对 F407 的接口没变**：一次流式 POST 没有逐块 HTTP 响应
⇒ 回执改由 **ESP 在转发循环里自己造**（每把一块写进 socket 就回一个 `0x04`）。F407 只认 `0x04`，**不关心它是谁造的**。

★★ **三条硬约束（ESP 侧实现时最容易踩）**
1. **窗口只能是 1** —— ESP 的 `Serial` RX 环**至多装一块**（要把它设成 **2048 = 正好一块**；⚠️ **core 默认只有 256**），
   而它读串口和 `client.write()` 是**同一根线程** ⇒ 连发两块必溢出、**静默丢字节**。**这不是性能取舍，是正确性。**
2. **`total` 是量化过的**：颗粒度是**半块 32 ms** ⇒ `total_blocks = seconds*1000/32/2` ⇒ **10 秒 = 156 块 = 319488 B = 9.984 s**，
   **不是** `10 × 32000 = 320000`。⚠️ 写错 ⇒ PC 侧判 `received == total` 对不上 ⇒ **整段录音永远不被识别、而且不报错**。**ESP 照抄 F407 给的 `total`，别自己算。**
3. **换行与分帧**：二进制帧**没有 `#`、也不是"行"** ⇒ ESP 的收帧处**必须先判 `0xA5 0x5A` 分流**，
   二进制走字节状态机、文本仍走行路径。★ `handleF407Receive()` 的**四个调用点一个都不能漏**。

## 3. 上行帧与异常事件（F407 → ESP → 云端）

### 3.1 常规上行帧

```
F407→ESP:  @SENSOR:温度:28.5,湿度:65\n              # 周期上报传感器数据（云端只记录，不调 AI）
F407→ESP:  @USER:你是谁呀\n                         # 用户请求（经 ESP → 云端 → AI）
```

### 3.1.1 `@SENSOR:` 结构化格式（★ 2026-09-15 正式定稿）

**这是"数据可视化"的地基**：云端统计页、异常判定、人员页全都按这个格式解析。
**现在 F407 端还没实现**（`main.c` 里 `@SENSOR` 零匹配，DHT11 驱动写了但从没被调用、
已被链接器 dead-strip），但格式先定死，硬件到位后**按这个发就行，云端一行不用改**。

```
@SENSOR:温度:28.5,湿度:65,距离:42,人:有
```

| 键 | 含义 | 取值 | 服务端字段 |
|---|---|---|---|
| `温度` | 摄氏度 | 数字，可负/可小数 | `temp` |
| `湿度` | 相对湿度 % | 数字 | `humi` |
| `距离` | 障碍物/人的距离 cm | 数字 | `distance` |
| `人` / `雷达` | 人员在离 | `有` / `无` | `presence`（`有`=1，`无`=0） |

规则：

- **中文 `键:值`，逗号分隔**；**缺项可以省略**（比如没接距离就只发温湿度）。
- `人:有` 和 `雷达:有` **两个键都认**（毫米波雷达 / 超声波推断都能用，谁方便用谁）。
- **全缺 / 读不到 → 就发 `@SENSOR:无数据`**。服务端把它记为 `valid=0`，
  **不入任何统计、不进图表**（老版趋势图就是栽在这上面：7600 行里绝大多数是 `无数据`，却画了 7600 个假点）。
- 解析器也认英文兜底（`temp:` / `humi:` / `t:` / `h:`），但**上报统一用中文**。

⚠️ **阈值判定在服务端做**（见 `analytics.evaluate_thresholds()` 和 `config.json::thresholds`），
**F407 端不需要自己判断异常** —— 这样改阈值不用重新烧固件。
F407 只管"读传感器 → 拼字符串 → 发出去"。

> 现在想看效果：打开网页「测试」页，有 8 个传感器预设按钮（正常/高温/低温/高湿/距离过近/有人/无人/无数据），
> 点一下填进输入框，再点「发送测试请求」即可。**这条链路已经全通并实跑验证过。**

### 3.2 @ALERT 异常/事件帧（预留接口）

```
F407→ESP:  @ALERT:温度过高，房间很热\n
```

| 项 | 值 |
|---|---|
| 触发时机 | F407 传感器/逻辑检测到异常或"值得让 AI 介入的事件"（温度越界、有人靠近、连续超时…） |
| ESP 行为 | 收到即当用户消息上报：`POST /api/data {user:"温度过高…", need_ai:true}`（**不等 30s 周期**） |
| 云端行为 | `need_ai=true` → 强制调用 AI 决策，返回信封 JSON |
| 当前状态 | ESP 已预留解析分支；**F407 端发送逻辑下一轮随字库一起做**。可先用网页「测试」页的「模拟异常 / 事件」面板验证全链路 |

> **⚠️ 注意区分两类异常**（2026-09-15 起）：
> - **设备自己报的**（`@ALERT:` / `POST /api/data` 的 `alert` 字段）→ `events.source='device'`
> - **服务端按阈值判出来的**（`config.json::thresholds`，见 3.1.1）→ `events.source='threshold'`
>
> **能走阈值判定的就别让 F407 报**：阈值改一下不用重烧固件，而且服务端有冷却（`cooldown_sec`），
> 不会因为温度持续偏高就刷屏式灌事件。`@ALERT:` 留给"阈值表达不了"的情况
> （比如"连续 3 次读取失败"这种需要 F407 自己看的逻辑）。

### 3.2.1 `POST /api/data` 的 `alert` 字段（★ 2026-09-15 新增，**可选，向后兼容**）

给"设备自己报的异常"一个**结构化**的入口（老的 `@ALERT:描述` 只有一段文本，没有 code/等级）。
**ESP 不发这个字段也照常工作**，所以 ESP 端可以先不动。

```json
POST /api/data
{
  "sensor": "温度:28.5,湿度:65",
  "alert":  { "code": "F407_SERVO_STALL", "severity": "error", "message": "舵机1 堵转" },
  "need_ai": false
}
```

- `alert` 可以是**对象**（推荐，能带 code/severity），也可以是**字符串**（等价于只给 message，code 自动补 `DEVICE_ALERT`）。
- `severity` 取值同阈值：`info` / `warn` / `error`。
- 写了就记一条 `events`（`source='device'`），**`need_ai` 不受影响** —— 要不要叫 AI 仍由 `need_ai` 决定。
- 老的 `@ALERT:温度过高，房间很热` 这种纯文本仍会被 `analytics.match_legacy_alert()` 兜底识别
  （按关键词匹配成 code），历史数据不会丢。

> 设计原因：AI **不常驻**。周期上报只记录不调 AI（省 token）；只有"用户主动请求"或"异常/事件上报"才触发决策。

### 3.3 need_ai 机制（云端 app.py）

```
run_ai = (不是测试模式) 且 (need_ai=True 或 user 非空)
run_ai 为假 → 只写 data_history，返回 {"action":"none","value":0,"message":"已记录（未调用AI）","ai":false}
               ESP 看到 ai:false 不会转发任何帧
```

### 3.4 ★★ 音频上行（ESP → PC）：**不走信封，走一条独立的流式 POST** ★ 2026-09-21 新增

> ★ 这条**不经过云端决策链路**：音频是**裸二进制**，进不了上面那套 JSON 信封 —— 它有自己的端点。

**端点**：`POST /api/audio/stream?token=<口令>&sess=<会话号>`，正文 **`Transfer-Encoding: chunked` 的裸 PCM 流**。
★ **一次录音只发一条 POST**（不是每块一条）。**放行靠 query token**（ESP 没有 session）。

**为什么不是"每块一次 POST"**：**werkzeug 3.1.8 不支持保活** —— 每个响应都带 `Connection: close`
⇒ 每块一条 POST 就是 10 秒 **156 条 TCP 连接**，ESP 上不可接受。（P0 实测，三条零安装的保活改法全试过、全无效。）

**配套端点**（P2 老路径仍在、**没被改坏**）：
`/api/audio/chunk`（分块）、`/api/audio/end`、`/api/audio/status`、`/api/audio/send`、`/api/audio/drop`、`/api/audio/mode`。

**`/api/audio/status` 的字段**（网页端判"录完了"用）：
`{"mode", "model", "last", "pending", "live", "wav_dir"}` —— ★ **`live` 是列表**（在收的会话），`last` 是字典或 `None`。
★ 判"录完了"用 **`live` 长度 1→0**，但**必须先观察到 `live.length >= 1` 再判 0**（会话注册之前 `live` 是 `[]`，第一次轮询就会误触发），
再加一个客户端 **`n + 15` 秒兜底**（`SESSION_IDLE_SEC = 30` 会回收卡住的会话）。

**三个"静默失效"的坑（PC 侧已钉成永久用例，谁改回去当场红）**
1. `total` 写成 `秒数 × 32000` ⇒ `complete:false` ⇒ **静默不识别**
2. 中途断流 ⇒ 残件（`44 + 实收` 字节）**不进识别队列**、会话槽释放
3. 并发复用同一个 `sess` ⇒ **409**（顺序复用无害）

## 4. 字库 font_lib（屏幕文字的字符白名单）

AI 决策里的 `message`/`text` 最终要靠 F407 的字库渲染成画面。字库**一个字一个像素表**，很占空间——所以不把整个字库塞给 AI，而是给它一份**小字符白名单**，让 AI 只从里面组词。

### 4.1 config.json 里的配置

```json
"font_lib": {
  "mode": "off",
  "charset": ["你","我","他","好","呀","再","见","热","冷","谢","累","的","了","在","不","请","来","去","真","棒","爱","困","怕","吗","呢"],
  "max_text_len": 12
}
```

| 字段 | 含义 |
|---|---|
| `mode` | `"off"` = 字库未开放，AI 不限字但要简短；`"charset"` = 只用白名单里的字 |
| `charset` | 白名单字符数组，用户提供字库后把**字库实际含有的常用字**填进来 |
| `max_text_len` | 屏幕一次最多显示的字数，AI 组词不能超过它 |

### 4.2 两种模式怎么用、何时切换

| mode | AI 行为（_build_system_prompt 注入一行约束） | 什么时候用 |
|---|---|---|
| `off` | "字库未开放，不限字，但尽量简短、多用常见字" | **字库还没到位时**（默认）。此时 F407 显示文字先凑合 |
| `charset` | "message/text 只能由白名单字拼成，且 ≤ max_text_len 字" | 字库到位后。白名单 = 字库覆盖的常用字 |

> **省 token**：白名单永远是一行以内，几乎不占上下文。
> 如果担心每次把 charset 列进 prompt 也费 token，把 `mode` 关回 `off` 即可——不会因为"读取整个字库"而爆上下文。
> 真正的字库二进制只存在于 F407 flash，从不进云端 prompt。

### 4.3 扩展 charset

F407 字库里新烧了哪些字，就把哪些字加进 `charset` 数组，AI 就会用到它们。不用改协议。

## 5. 兼容性（v1 → v2）

- **老决策也能解析**：云端 `parse_decision` 遇到没有 `moves` 的旧数据（`{"action":"fan_on","value":1,...}`）会自动包成一条 `{"type":"fan_on","value":1,...}`。
- **老记录照常显示**：网页决策历史里新旧两代都能渲染——有 `moves[]` 显示动作概要，没有就回退显示 action/value。
- **ESP 兜底**：收到不含 `moves` 但含 `action` 的旧响应时，合成一条 `@MOVE:action,value`，保证不会静默丢命令。
- **F407 旧帧**：v1 时代 F407 的 `@AI:` 整包帧格式作废，由 `@MOVE:`/`@TEXT:` 取代（F407 端解析下一轮统一实现）。
