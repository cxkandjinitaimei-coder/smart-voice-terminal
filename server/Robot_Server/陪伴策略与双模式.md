# 陪伴策略与双模式（云端决策 + ESP 运行模式）

> 目标：让 AI 决策**带上真实可用的动作参数**（不只是空话），并约定 ESP 两种运行模式。
> 原则：**约束写在配置里，方便以后改**；F407 / ESP 代码分轮落地，本轮先把云端策略跑通。

相关协议见《[决策协议v2.md](决策协议v2.md)》。

---

## 1. 硬件动作约定（脖子两舵机）

屏幕是脸，两颗舵机是脖子。**中值默认都是 90°**（上电归中）。

| 舵机 | 语义 | 安全角度 | 说明 |
|---|---|---|---|
| **id=1** | 点头（俯仰） | **75° ~ 105°**（中值 90° ±15°） | 幅度小，避免屏幕磕到 / 线材拉扯 |
| **id=2** | 左右转头（偏航） | **0° ~ 180°**（中值 90° ±90°） | 可左右大幅转向看人 |

### 决策里怎么写

```json
{"type":"servo","id":1,"angle":100}   // 轻微抬头/点头方向
{"type":"servo","id":2,"angle":45}    // 看向左侧
{"type":"gesture","name":"nod"}       // 交给 F407 做「点头」联动（内部仍应夹在 75~105）
```

### 约束落点（分层，方便改）

| 层 | 职责 |
|---|---|
| **云端 config `hardware.servos`** | 告诉 AI 合法范围，减少越界决策 |
| **ESP（可选）** | 转发前可再夹一次角度（防呆） |
| **F407 执行层（最终兜底）** | 无论上游给什么，执行前强制 clamp 到安全范围 |

> 以后要改角度：优先改 `config.json` 的 `hardware.servos`；F407 固件里的宏同步改。
> 功能不局限这两颗舵机——新设备继续往 `moves[]` 加新 `type` 即可（见决策协议 v2）。

### 常用 gesture 与舵机的关系（建议）

| gesture | 建议映射（F407 实现时） |
|---|---|
| `nod` | 舵机1 在 75~105 内做一次点头后回中 |
| `hi` | 舵机2 小幅左右摆 + expression happy |
| `look_left` / `look_right` | 舵机2 → 约 45° / 135° |
| `shake` | 舵机2 左右小幅摇头 |

具体轨迹表放 F407，云端只输出 `gesture` 名字或直接给 `servo` 角度。

## 2. ESP 双模式：待机 / 全功率

ESP 作为桥，有两种运行模式（**模式状态主要在 ESP，可上报给云端**）：

| 模式 | 何时 | AI 怎么调 | 上报节奏（建议） |
|---|---|---|---|
| **idle 待机省电** | 附近没人 / 用户强制待机 | **只对异常/事件**（`@ALERT` 或 `need_ai` 由异常触发）做决策；普通 `@USER:` / 闲聊**不调 AI** | 周期上报可加长（如 60s），sensor 可报「无数据」 |
| **full 全功率** | 有人在旁 / 用户强制全功率 | **用户每一次输入都要 AI 决策**（`need_ai=true`）；异常同样触发 | 上报更勤（如 10~30s），传感器照常 |

### 切换规则（用户优先级最高）

```
优先级从高到低：
  1) 用户自定义强制   →  锁定该模式，直到用户再改
  2) F407 探测结果    →  有人 → full；无人 → idle（仅当未被用户锁定时）
```

| 来源 | 帧 / 方式（建议） | 效果 |
|---|---|---|
| 用户强制 | 网页 / 串口 / 将来 App 下发；或 F407 转发用户选项 `@MODE:full` / `@MODE:idle` / `@MODE:auto` | `full`/`idle` = 锁定；`auto` = 解除锁定，改回听 F407 |
| F407 探测 | 超声波等判断有人/无人 → `@MODE:full` 或 `@MODE:idle`（仅 auto 时生效）；也可塞在 `@SENSOR:` 里带 `人:有/无` | 自动切换 |

> 本轮：**语义与云端策略先落地**；ESP 真正维护 `mode` / `user_lock` 状态机、解析 `@MODE:` —— **下一轮改 sketch**。
> 云端本轮已认识上报字段里的 `mode`（见下），网页模拟异常也可带上。

### 和 need_ai 的关系（目标行为）

```
ESP 侧（目标）：
  if mode == full:
      有 user 输入 → need_ai = true
      仅周期 sensor → need_ai = false
  if mode == idle:
      仅当本包来自 @ALERT / 明确异常 → need_ai = true
      普通 user 文本 → 可先缓存或本地提示「待机中」，不上报 AI
      周期 sensor → need_ai = false
```

云端仍以收到的 `need_ai` / `user` 为准；**模式字段 `mode` 进 prompt**，让 AI 知道当前是陪伴还是省电语境。

### 定时唤醒：让机器人自己先开口（2026-09-13 已实现）

上面那一套都是「用户/异常来了才响应」。**定时唤醒**补上另一半：服务器每 `auto_tick.interval_sec`
秒主动调一次 AI，让机器人自己找话（= 真陪伴，不是问答机）。相当于嵌入式里的定时器中断 ——
定时器在服务器侧跑，到点了就干一次活。

**它是"主动"但不"烦人"，靠三道闸**（任一不满足就跳过，**不调 AI、不花钱**）：

| 闸 | 判据 | 为什么 |
|---|---|---|
| 设备在线 | 最近 `DEVICE_ONLINE_SEC`(90s) 内有上报 | 离线时触发的命令会堆在队列里，等它重连后一次性全放出来，像卡带 |
| 队列空 | `max_queue`（默认 1） | 定时器不该把命令队列刷爆，一次只留一条等执行 |
| 静默期 | 距上次用户说话 < `quiet_sec`（默认 60s） | **人在说话时机器人插嘴 = 最劝退的体验**，优先级低于用户 |

`require_online` 默认开，所以**还没烧 ESP / 设备没上线的阶段，定时器一次都不会触发、也不花钱** ——
接上硬件后才会真正开始"自己找话说"。

和双模式的关系：定时唤醒的 `mode` 默认跟 `modes.default`（现为 `full`）。若希望待机时少开口，
把它设成 `idle`，AI 的动作会更克制（见 §1 的规则落点）。

改参数：`config.json::auto_tick`，或运行中 `POST /api/auto_tick {"interval_sec":300}`，**不用重启**。

## 3. 上报给云端的数据处理

### 3.1 建议 body 字段（在现有基础上扩展）

```json
{
  "token": "YOUR_API_TOKEN",
  "sensor": "温度:28.5,湿度:65,距离:42,人:有",
  "user": "你好呀",
  "need_ai": true,
  "mode": "full"
}
```

| 字段 | 含义 | 空时 |
|---|---|---|
| `sensor` | 传感器摘要字符串 | ESP 已约定空 → `"无数据"` |
| `user` | 用户话 / 异常描述 | 空 = 周期上报 |
| `need_ai` | 是否强制调 AI | 由 ESP 按模式规则置位 |
| `mode` | `idle` / `full` | 缺省时云端当 `full` 或 `unknown`（可配置） |

### 3.2 sensor 字符串建议键（F407 拼、ESP 原样传）

便于云端 / 网页解析，也不破坏现有「整串透传」：

```
温度:28.5,湿度:65,距离:42,人:有
温度:--,湿度:--,距离:--,人:无
无数据
```

| 键 | 来源 |
|---|---|
| `温度` / `湿度` | DHT11 |
| `距离` | HC-SR04（cm） |
| `人` | F407 逻辑：`有` / `无`（可由距离阈值推断） |

### 3.3 云端处理策略（本轮）

1. **原样入库** `data_history`（记忆 / 趋势图继续用）
2. **拼进 AI 当前请求**：传感器 + 用户 + **当前 mode**
3. **rules / hardware** 约束 AI 输出的舵机角度与模式语义
4. 以后可加：云端对 sensor 做结构化解析（阈值告警、自动补 `@ALERT` 语义）——配置开关预留，不急着做

## 4. 云端配置项（本轮写入 config.json）

```json
"hardware": {
  "servos": [
    {"id": 1, "role": "nod",   "name": "点头俯仰", "mid": 90, "min": 75, "max": 105},
    {"id": 2, "role": "yaw",   "name": "左右转头", "mid": 90, "min": 0,  "max": 180}
  ],
  "sensors": ["dht11", "hcsr04"],
  "display": "lcd_face"
},
"modes": {
  "default": "full",
  "idle":  { "ai_on": "alert_only", "desc": "待机省电：仅异常/事件触发 AI" },
  "full":  { "ai_on": "every_user", "desc": "全功率：每次用户输入都决策" },
  "switch": {
    "priority": ["user_lock", "f407_detect"],
    "user_values": ["full", "idle", "auto"],
    "note": "用户强制优先；auto 时听 F407 有人/无人"
  }
}
```

- `ai_relay._build_system_prompt` 会把 `hardware.servos` 角度表和 `modes` 说明注入 prompt。
- 改角度 / 改模式语义 → **只改 config，尽量不改代码**。

## 6. 和现有 need_ai / @ALERT 的对齐

- **全功率**：行为 ≈ 现在（有 user 就调 AI）。
- **待机**：把「有 user 就调 AI」收窄为「仅异常调 AI」——靠 ESP 少报 `need_ai`，不是靠云端拒绝。
- **`@ALERT:`**：两模式都要响应；待机下这是 AI 的主要入口。
- **网页「模拟异常」**：继续 `need_ai=true`；以后可加 `mode` 下拉框做联调。
